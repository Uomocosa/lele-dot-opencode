# WORKFLOW SETUP — the blocking first phase of every Rust workflow skill

Every workflow skill (`refactor-workflow-rs`, `plan-remove-dead-code-rs`)
runs this setup **before** it inventories, audits, or proposes anything. Skipping a step is a
violation; the proof-of-setup block (step 6) makes a skipped step visible to the user.

## 1. Load skills

| When | Load |
|------|------|
| Always | `lele-rs`, then `lele-syntax-rs` |
| A crate under review depends on `bevy` | `bevy-rs` (and `avian-rs` for `avian2d`/`avian3d`) |
| … on `libp2p` / `freenet-stdlib` / `freenet` | `libp2p` / `freenet` |
| … on `serde`, `clap`, `jiff`, `rayon`, `criterion`, `itertools`, `reqwest` | the matching `*-rs` skill |
| The workflow touches `rust-toolchain.toml`, `justfile`, `prek.toml`, `.cargo/config.toml` | `rust-env-rs` (legacy `devenv.nix`: `devenv-rs-legacy`) |
| The crate has a `state_machine/` folder | `definition-state-machine` |

Decide from each crate's `Cargo.toml` `[dependencies]` and `[dev-dependencies]`, not from memory.

## 2. Read in full (the `skill` tool does not inline these)

- `~/.config/opencode/skills/lele-syntax-rs/references/RATIONALE.md`
- `~/.config/opencode/skills/lele-syntax-rs/references/SMELLS.md`
- The **mechanical rules**, generated by the installed linters (always current, no repo path):
  - `lele-lint --rules-md`
  - `lele-bevy-lint --emit rules-md` (only when a crate depends on `bevy`)

  At minimum read the rule *summaries* in full, and the full section (`lele-lint --explain <CODE>`)
  for every rule your proposals touch.
- Each repo's `justfile` — its recipes are the canonical verifiers.
- Each crate's `lele.toml` (boundaries, whitelists) and `clippy.toml`.

## 3. Baseline run

Before proposing anything, run per repo (PATH prefix and `2>&1`, never piped):

```bash
export PATH="$HOME/.cargo/bin:$HOME/.local/bin:$PATH" && just lint 2>&1
export PATH="$HOME/.cargo/bin:$HOME/.local/bin:$PATH" && just bevy-lint 2>&1   # when present
export PATH="$HOME/.cargo/bin:$HOME/.local/bin:$PATH" && just clippy 2>&1
```

Record every pre-existing finding as **baseline**. Baseline findings are never attributed to a
batch, and a batch is "green" when it adds no finding beyond the baseline.

## 4. Check proposals against the linter, not only the skills

- A name, move, or new type must pass every `LELE0xx`/`LELEBEVY0xx` rule. When a rule's exact
  behaviour matters (exemptions, prefix matching), read the checker, not only the summary.
- A type that passes only through an exemption (e.g. a `Serialize` derive nobody uses, which
  silences `LELE026`) is a **finding**, not a pass. Never propose keeping or copying the dodge.
- Known collisions to check: `methods/<type_snake>/` is keyed by type name, so two domains'
  `Plugin` types collide under `LELE030`; `LELE012` skips `__basic__/` files but the stutter is
  still a naming defect.

## 5. Conflicts between rule sets

The linter is authoritative; skills are guidance. When two sources disagree (e.g. `bevy-rs`
`plugin_build.rs` vs `LELE030` `methods/`, or `LELE026` vs a Bevy `Resource` that must wrap a
`Vec`), **stop and ask the user** with the options laid out. Never resolve a conflict silently.

## 6. Proof of setup — first lines of the first reply

```
Setup:
  Skills:   lele-rs, lele-syntax-rs, bevy-rs, freenet, …
  Read:     RATIONALE.md, SMELLS.md, lele-lint --rules-md, lele-bevy-lint --emit rules-md, justfile, lele.toml
  Baseline: lint ✅ | bevy-lint ❌ 2 (LELEBEVY005 overlay.rs:290, LELEBEVY008 spawn_connecting.rs:72) | clippy ✅
  Conflicts: <none | list, with the question to the user>
```

No proposal, table, or manifest may appear before this block.
